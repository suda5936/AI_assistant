역할: 앱 예외 계층과 처리기 등록. 코드·메시지는 02_design.md "오류 처리" 표가 기준이다.
```python
@dataclass(frozen=True)
class FieldError:
    field: str
    message: str

class AppError(Exception):
    status_code: int; code: str; message: str   # 하위 클래스가 클래스 속성으로 정한다

class ValidationFailedError(AppError):    # 422 validation_error
    def __init__(self, details: list[FieldError]) -> None: ...
class UsernameTakenError(AppError): ...       # 409 username_taken
class InvalidCredentialsError(AppError): ...  # 401 invalid_credentials
class NotAuthenticatedError(AppError): ...    # 401 unauthenticated

def error_body(code: str, message: str, details: list[FieldError] | None = None) -> dict[str, object]:
    """{"error": {"code", "message"[, "details": [{"field","message"}]]}} 를 만든다. details가 None이면 키를 넣지 않는다."""

def register_exception_handlers(app: FastAPI) -> None:
    """AppError, RequestValidationError, StarletteHTTPException, Exception 처리기를 등록한다.
    Exception 처리기는 logger.exception으로 기록하고 500 internal_error만 응답한다.
    RequestValidationError 처리기는 exc.errors()의 항목마다 FieldError(field_from_loc(item.get("loc")),
    "형식이 올바르지 않습니다.")를 만든다."""

def field_from_loc(loc: Sequence[str | int] | None) -> str:
    """loc에서 문자열인 요소 중 마지막 것을 돌려준다. loc이 None·빈 값이거나 문자열 요소가 없으면 "body".
    예: ("body","username")→"username", ("body",1)→"body", ("body",)→"body", ("query","page")→"page".
    (02_design.md "검증 오류 field 규칙")"""
```
예외 클래스 이름은 하네스 ruff 규칙 N818에 따라 `Error`로 끝난다(`AppError` 포함). 이후 추가하는 예외(M2의 404·403 등)도 같은 규칙을 따른다.

### services/passwords.py (ADR 0001)
```python
def hash_password(password: str) -> str:
    """16바이트 무작위 솔트(secrets.token_bytes)와 hashlib.scrypt(n=16384, r=8, p=1, dklen=64)로
    'scrypt$16384$8$1$<salt_b64>$<hash_b64>'(표준 base64)를 만든다. 같은 비밀번호도 매번 다른 값.
    전제: password는 UTF-8로 인코딩 가능해야 한다(호출 전에 check_password로 걸러진다).
    Raises: UnicodeEncodeError(ValueError 하위) - 짝 없는 서로게이트 등 UTF-8로 인코딩할 수 없을 때"""

def verify_password(password: str, stored_hash: str) -> bool:
    """stored_hash의 파라미터·솔트로 다시 계산해 hmac.compare_digest로 비교한다.
    형식이 깨진 stored_hash거나 password를 UTF-8로 인코딩할 수 없으면 예외 없이 False."""

def verify_dummy(password: str) -> None:
    """존재하지 않는 아이디로 로그인할 때 응답 시간을 맞추려고 모듈 안에 한 번만 만든 더미 해시로 verify_password를 수행한다."""
```

```python
PASSWORD_MIN_LENGTH = 8; PASSWORD_MAX_LENGTH = 72

def check_username(raw: str) -> tuple[str | None, FieldError | None]:

    '비밀번호에 사용할 수 없는 문자가 포함되어 있습니다.', 아니면 None. 앞뒤 공백도 문자로 센다.
    예외를 밖으로 내보내지 않는다."""

def validate_signup(username_raw: str, password: str) -> str:
    """두 검사를 모두 수행해 정규화된 username을 돌려준다.
    Raises: ValidationFailedError - 오류가 하나라도 있으면 [username 오류, password 오류] 순서로 담아서
    """
```

### services/users.py
```python
def create_user(db: Session, username_raw: str, password: str, now: datetime) -> User:
    """validate_signup → 같은 username이 있으면 UsernameTakenError → hash_password로 저장 후 commit.
    INSERT에서 IntegrityError(동시 가입)가 나면 rollback 후 UsernameTakenError.
    Raises: ValidationFailedError, UsernameTakenError
    """

def authenticate(db: Session, username_raw: str, password: str) -> User:
    """아래 순서로 검사하고, 실패하면 원인과 무관하게 같은 InvalidCredentialsError(같은 메시지)를 던진다.
    1. len(password) > PASSWORD_MAX_LENGTH(72)면 DB 조회와 scrypt 없이 바로 실패한다.
       이 검사는 반드시 사용자 조회보다 먼저 한다(아이디 존재와 무관한 경로가 되도록).
    2. username_raw.lower()로 조회한다. 아이디를 UTF-8로 인코딩할 수 없으면(짝 없는 서로게이트)
       그런 사용자는 있을 수 없으므로 '사용자 없음'과 같은 경로로 처리한다(500 아님).
    3. 사용자가 없으면 verify_dummy(password) 후 실패한다.
    4. 사용자가 있으면 verify_password(password, user.password_hash)가 False일 때 실패한다.
    불변 조건: 같은 password에 대해 scrypt 계산 횟수는 아이디 존재 여부와 무관하다
    (72자 초과 0회, 그 밖에는 verify_password 또는 verify_dummy 중 정확히 1회 호출).
    UTF-8 인코딩 불가 비밀번호는 verify_password/verify_dummy가 양쪽 다 scrypt 전에 False를 내므로
    같은 InvalidCredentialsError(500 아님)이며 이 불변 조건도 지켜진다.
    Raises: InvalidCredentialsError
    """
```

### hooks/useAuth.ts, components/AuthProvider.tsx
```ts
export type AuthStatus = "loading" | "ready";
export interface AuthContextValue {
  user: User | null;
  status: AuthStatus;

  logout(): Promise<void>;  // 아래 "logout 계약". 성공·401이면 user=null, 그 밖의 실패는 user 유지 + 오류를 다시 던진다
```

- 마운트 시 `getMe()`를 한 번 호출한다. 결과로 user를 정하고 status를 "ready"로 바꾼다. 오류가 나면 user=null, "ready"로 둔다 (AC-8: 새로고침 후 복원).
- 사용자 정보는 메모리(Context)에만 둔다. localStorage에 저장하지 않는다.
- 로그인 여부의 출처는 AuthProvider의 `user` 하나뿐이다. 다른 컴포넌트(Header 포함)는 사용자를 숨기거나 덮어쓰는 로컬 state를 두지 않는다.

#### logout 계약 (AuthProvider.tsx, T-07 산출물을 T-09에서 수정)
`authApi.logout()`의 결과에 따라 다음과 같이 한다.

| authApi.logout() 결과 | user | logout()의 결과 |
|---|---|---|
| 성공(204) | `null`로 바꾼다 | resolve |
| `ApiError`이고 `status === 401` (서버 세션이 이미 없음) | `null`로 바꾼다 | resolve (성공과 같게 취급, 던지지 않음) |
| 그 밖의 모든 실패 (`ApiError` 500, `status 0` network_error, `unknown_error` 등, `ApiError`가 아닌 예외 포함) | 바꾸지 않는다 (로그인 유지) | 받은 오류를 그대로 다시 던진다 |

- AuthProvider는 화면 상태(요청 중 여부, 안내 문구)를 갖지 않는다. 그것은 Header의 몫이다.
- 401 행 참고: 현재 백엔드 계약상 `POST /api/auth/logout`은 쿠키가 없거나 무효해도 204라 401을 내지 않는다. 그래도 프록시·다른 경로에서 401이 오면 "세션이 이미 없다"는 뜻이므로 로그인 상태로 남겨 두지 않는다(PM 결정).
- `status`는 logout과 무관하다(계속 "ready").

### components/Header.tsx
- `<header>` 안에 홈 링크 "게시판"(`/`).
- status가 "loading"이면 인증 영역을 그리지 않는다.
- 비로그인(`user === null`): 링크 "로그인"(`/login`), "회원가입"(`/signup`).
- 로그인: `<span data-testid="current-username">{user.username}</span>`, `<button type="button">로그아웃</button>`.
- 로그인 여부는 `useAuth().user`만 보고 정한다. 사용자를 숨기는 로컬 state(이전 구현의 `hiddenUser`)는 두지 않는다.
- Header가 갖는 로컬 state는 두 개뿐이다: `loggingOut: boolean`(요청 중), `logoutFailed: boolean`(직전 시도 실패).
- 로그아웃 버튼을 누르면:
  1. `loggingOut=true`, `logoutFailed=false`로 바꾼다. 요청 중에는 버튼에 `disabled`를 준다(연타해도 요청은 한 번).
  2. `await logout()`.
  3. resolve(성공 또는 401): `navigate("/")`. 화면은 AuthProvider의 `user=null`로 비로그인이 된다.
  4. reject(그 밖의 실패): `logoutFailed=true`. 아이디와 로그아웃 버튼은 그대로 보이고(로그인 유지), 이동하지 않는다. 오류는 이 안내로 처리한 것이며 다시 던지지 않는다.
  5. 끝나면(성공·실패 모두) `loggingOut=false`.
- `logoutFailed`이면 로그인 영역 안(로그아웃 버튼 뒤)에 `<p role="alert">로그아웃하지 못했습니다. 다시 시도해 주세요.</p>`를 보여 준다. 문구는 오류 종류와 무관하게 고정이다(서버 message를 쓰지 않는다). 다시 누르면 1에서 안내가 사라지고, 성공하면 비로그인 영역으로 바뀌어 안내도 보이지 않는다.
- 역할 분담 요약: AuthProvider = 서버 호출과 `user` 변경(로그인 상태의 유일한 출처), Header = 요청 중 버튼 비활성화, 실패 안내 표시, 성공 시 `/` 이동.

### pages/SignupPage.tsx (`/signup`)
- `<h1>회원가입</h1>`, `<label>아이디</label>` 입력(`autoComplete="username"`), 안내 문구 "영문 소문자, 숫자, 밑줄(_) 4~20자 (대문자는 소문자로 저장됩니다)", `<label>비밀번호</label>` 입력(type=password, `autoComplete="new-password"`), 안내 "8~72자", `<button type="submit">가입하기</button>`.
- 클라이언트 측 검증은 하지 않는다. 서버 응답이 검증의 기준이다.
- 422: `details`를 field별로 해당 입력 아래 `<p role="alert">`에 표시한다. 409: username 입력 아래에 message를 표시한다. 그 밖의 ApiError: 폼 위 `<p role="alert">`에 message.
- 422인데 표시할 field가 없을 때(`details`가 비었거나, `field`가 `username`·`password`인 항목이 하나도 없을 때. 예: `field: "body"`): 폼 위 `<p role="alert">`에 응답의 `message`를 표시한다. 화면에 오류가 하나도 보이지 않는 경우가 없어야 한다. `username`·`password` 항목이 하나라도 있으면 그 항목만 입력 아래에 표시하고, 나머지 field는 버린다(폼 위 message는 표시하지 않는다). 단위 테스트: `details: [{ field: "body", ... }]`인 422에서 폼 위 alert에 message가 보인다. (M2 게시글 폼도 같은 규칙을 따른다.)
- 성공: `navigate("/login", { state: { signedUp: true } })` (Q8).
- 제출 중에는 버튼을 비활성화한다.

### pages/LoginPage.tsx (`/login`)

- `location.state?.signedUp`이면 `<p role="status">가입이 완료되었습니다. 로그인해 주세요.</p>`.

### App.tsx, main.tsx
- `main.tsx`: `createRoot(document.getElementById("root")!)`에 `<StrictMode><BrowserRouter><AuthProvider><App/></AuthProvider></BrowserRouter></StrictMode>`를 렌더링한다. 이 구성은 main.tsx에만 둔다(App.tsx는 Router·Provider를 만들지 않는다). 최종 형태로 만드는 담당은 T-08이다.
- `App.tsx`: `<Header/>` + `<main><Routes>` (`/`, `/signup`, `/login`, `*`).
- main.tsx 구성 확인 테스트 (`frontend/src/main.test.tsx`): main.tsx는 커버리지 측정에서만 제외되고, 테스트에서 import하는 것은 허용된다. 실제 main.tsx를 import해서 구성 전체를 확인한다.
  1. `vi.mock("./api/auth")`로 `getMe`는 `null`을 돌려주게 한다(네트워크 호출 없음).
  2. `document.body.innerHTML = '<div id="root"></div>'`, `window.history.pushState({}, "", "/login")`.
  3. `await act(async () => { await import("./main"); })`.
  4. `await screen.findByRole("heading", { name: "로그인" })`이 보인다. `/login`은 BrowserRouter(라우팅)와 AuthProvider(LoginPage의 useAuth) 둘 다 있어야 그려지므로, 둘 중 하나라도 빠지면 이 테스트가 실패한다.
  - 테스트는 이 하나로 충분하다. StrictMode 때문에 `getMe` 호출 횟수가 달라질 수 있으므로 호출 횟수는 단언하지 않는다. 이 파일 안에서 main을 두 번 import하지 않는다(모듈 캐시 때문에 두 번째는 렌더링되지 않음).

- T-06에서 `npm install`로 `package-lock.json`을 만들어 커밋 대상에 포함한다. `vite`, `vitest`, `@vitest/coverage-v8`(및 짝이 되는 `@vitejs/plugin-react`)은 02_design.md "프론트 도구 버전 규칙"대로 `npm audit --audit-level=high`를 통과하는 가장 낮은 메이저로 올리고, developer가 npm으로 정확한 버전을 확정해 lock에 고정한 뒤 완료 보고에 적는다. 그 밖의 패키지는 audit 실패 시 같은 메이저 안에서 올린다. audit 기준 완화, `overrides`, `--force`는 쓰지 않으며, 그래도 안 되면 PM에게 보고한다.
- `tests/acceptance/`가 없으면 `$(wildcard ...)`로 빠지므로 qa가 만들기 전에도 `make check`가 동작한다.
- 백엔드 개발 도구 버전은 02_design.md "기술 스택"과 "백엔드 도구 버전 규칙"을 따른다: `backend/pyproject.toml`의 dev 의존성은 `pytest>=9.0.3,<10`, `pytest-cov>=6,<8`(나머지는 그대로). `backend/Makefile`의 `setup`은 venv 생성 → `.venv/bin/python -m pip install --upgrade pip` → `.venv/bin/python -m pip install -e ".[dev]"` 순서다. 반영 후 `make check`, `make coverage`, `make audit`(백엔드 부분)가 통과해야 하며, 설치된 pytest·pytest-cov·pip 버전을 완료 보고에 적는다.

## 통합 검증 시나리오
qa가 `make e2e`(ui·api)와 `tests/acceptance/`로 확인한다. 데이터는 실행마다 고유한 아이디(`u` + 타임스탬프, 소문자·숫자 20자 이내)를 쓴다.

1. 비로그인 상태로 `/`에 접속하면 헤더에 "로그인", "회원가입" 링크가 있고 아이디는 없다.
2. 회원가입: 아이디 `ab`로 가입하면 형식 사유가, 비밀번호 7자로 가입하면 "비밀번호는 8자 이상이어야 합니다."가 보인다(AC-3, AC-4). 아이디 칸에 공백만 넣으면 "아이디를 입력해 주세요."가 보인다.
3. 정상 아이디·8자 비밀번호로 가입하면 로그인 화면으로 이동하고 "가입이 완료되었습니다. 로그인해 주세요."가 보인다(AC-1, Q8).
4. 같은 아이디를 대문자로 바꿔 다시 가입하면 "이미 사용 중인 아이디입니다."가 보인다(AC-2).
5. 틀린 비밀번호, 존재하지 않는 아이디로 각각 로그인하면 둘 다 "아이디 또는 비밀번호가 올바르지 않습니다."가 보이고 헤더는 비로그인 상태다(AC-7).
6. 올바르게 로그인하면 `/`로 이동하고 헤더에 내 아이디가 보인다(AC-6). 새로고침해도 아이디가 보인다(AC-8).
7. 세션 쿠키 `board_session`은 `httpOnly=true`이고 `document.cookie`로 읽을 수 없다(AC-10).
8. 로그아웃하면 헤더가 비로그인 상태로 바뀐다. 로그아웃 전에 저장해 둔 쿠키로 `GET /api/auth/me`를 보내면 401 `unauthenticated`다(AC-9).
   - 8-1. 로그인 상태에서 `page.route("**/api/auth/logout", ...)`로 응답을 500으로 바꾼 뒤 로그아웃을 누르면 헤더에 아이디가 그대로 있고 "로그아웃하지 못했습니다. 다시 시도해 주세요."(role=alert)가 보인다. route를 해제하고 다시 누르면 비로그인 상태가 된다(AC-9).
9. API: 가입·로그인·me 응답 본문에 `password`, `password_hash` 키와 해시 문자열이 없다(AC-10). `Content-Type: text/plain`으로 `POST /api/auth/login`을 보내면 415다. 오류 응답은 모두 `{"error": {"code", "message"}}` 형식이다.
10. 인수 테스트: 가입 후 테스트 DB를 직접 조회하면 `password_hash`가 평문과 다르고 `scrypt$`로 시작하며, 같은 비밀번호의 두 계정 해시가 서로 다르다(AC-5).
