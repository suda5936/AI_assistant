## 보안 조건 (M2 전체에 적용, reviewer·security-reviewer 확인 대상)
1. **이동 경로에 사용자 입력을 쓰지 않는다.** `navigate()`, `<Link to>`, `<Navigate to>`의 대상은 다음 둘 중 하나로만 만든다.
   - 앱 안의 고정 경로 문자열: `"/"`, `"/login"`, `"/signup"`, `"/posts/new"`
   - 템플릿에 **숫자**만 넣은 경로: `` `/posts/${post.id}` ``, `` `/posts/${post.id}/edit` ``(서버가 준 `number`), `` `/?page=${page ± 1}` ``(서버 응답의 `page`로 계산한 `number`)
   - `?next=`, `?redirect=`, `location.state`의 경로, URL 쿼리·해시 문자열을 이동 대상으로 쓰지 않는다. 로그인 후에는 언제나 `/`로 간다(M1 그대로).
2. **URL의 글 ID는 검사한 뒤에만 API 경로에 넣는다.** 라우트 파라미터 `:id`는 `parsePostId()`(정규식 `^[1-9][0-9]{0,15}$` + `Number.isSafeInteger`)를 통과한 `number`만 `api/posts.ts`에 넘긴다. 통과하지 못하면 API를 부르지 않고 "게시글을 찾을 수 없습니다." 화면을 보여 준다. 목록의 `?page=` 값은 `URLSearchParams`로 인코딩해 쿼리로만 보낸다(경로에 넣지 않음).
3. **CORS를 열지 않는다.** `CORSMiddleware`를 추가하지 않고, 어떤 응답에도 `Access-Control-Allow-*` 헤더를 넣지 않는다(`allow_origins=["*"]` + credentials 포함 금지). CSRF 방어(SameSite=Lax + JSON 전용 415)가 이 전제에 기대고 있다.
4. **상태 변경 요청은 JSON으로 보낸다.** `DELETE /api/posts/{id}`도 `Content-Type: application/json`과 본문 `{}`를 보낸다(`client.ts`가 이미 그렇게 한다. 바꾸지 않는다).
5. **사용자 글은 텍스트로만 그린다.** 제목·내용·아이디는 JSX 텍스트 노드로만 렌더링한다. `dangerouslySetInnerHTML`, `innerHTML`, `eval`을 쓰지 않는다(eslint `react/no-danger` 유지). 서버는 HTML을 이스케이프하거나 걸러 내지 않고 입력 그대로 저장·응답한다(AC-25 "입력한 글자 그대로").
6. **상태를 바꾸는 GET을 만들지 않는다.** 글 삭제는 DELETE로만 한다.

### api/middleware.py (추가)
```python
def register_body_limit_middleware(app: FastAPI, max_bytes: int) -> None:
    """/api/ 아래 POST·PUT·PATCH·DELETE 요청의 본문 크기를 헤더만 보고 제한한다. 본문을 읽지 않는다.
    아래 순서대로 판정하고, 처음 걸린 것으로 응답한다(순서를 바꾸지 않는다).
      1. Transfer-Encoding 헤더가 하나라도 있으면(값·대소문자 무관, Content-Length 유무 무관) 411.
      2. Content-Length 헤더가 2개 이상이면 411. (request.headers.getlist("content-length"))
      3. Content-Length 헤더가 1개면:
         a. 값의 앞뒤 공백 문자를 str.strip()으로 지운 뒤, 남은 값이 ASCII 10진 숫자
            ([0-9]+, 빈 문자열·중간 공백·부호·쉼표 불가)가 아니면 411.
            예: " 10"·"10 " → 10으로 판정, "1 0"·"+10"·"1,0"·"" → 411.
         b. 앞의 "0"을 모두 뗀 유효 숫자의 자릿수가 len(str(max_bytes))보다 많으면 int() 없이 413.
         c. 그 밖에는 int(유효 숫자)(빈 문자열이면 0) > max_bytes면 413.
      4. 둘 다 없으면(본문 없음) 통과.
    411: error_body("length_required", "요청 본문의 길이를 알 수 없습니다.")
    413: error_body("payload_too_large", "요청 본문이 너무 큽니다.")
    """

def register_security_headers_middleware(app: FastAPI) -> None:
    """모든 응답(경로 무관, 415·411·413·404 포함)에 config.SECURITY_HEADERS를 설정한다(이미 있으면 덮어쓴다).
    X-Content-Type-Options: nosniff
    X-Frame-Options: DENY
    Content-Security-Policy: default-src 'none'; frame-ancestors 'none'
    """
```
- 경로 판정은 기존 `json_only`와 같다(`request.url.path.startswith("/api/")`, 메서드 집합 `STATE_CHANGING_METHODS` 재사용).
- **1번(Transfer-Encoding)이 Content-Length보다 먼저인 이유**: 두 헤더가 함께 오면 ASGI 서버(h11 등)는 RFC 7230 3.3.3대로 Transfer-Encoding을 따라 청크 본문을 끝까지 읽는다. Content-Length만 보고 통과시키면 상한이 우회된다(T-13 리뷰 r1 Major #1, 실제 2MB 가입이 201). 정상 클라이언트(브라우저 `fetch`, 프론트 `client.ts`)는 JSON 문자열 본문에 항상 Content-Length를 쓰므로 청크 전송을 막아도 영향이 없다.
- 2번·3b번은 같은 원칙(길이를 확정할 수 없으면 거부, 예외로 500을 내지 않음)이다. 3b는 숫자가 4300자를 넘을 때 `int()`의 `ValueError`로 500이 나는 것을 막는다(T-13 리뷰 r1 Minor #2).
- 3a의 앞뒤 공백 제거: 실제 서버(uvicorn + h11)는 헤더 값의 앞뒤 공백(OWS)을 이미 지워서 앱에 넘기므로 실제 동작에는 차이가 없다. 길이 값 자체는 그대로 해석하므로 우회 경로가 아니다(T-13 리뷰 r2 Minor #1, 현재 코드 `lengths[0].strip()` 유지, 코드 수정 없음).
- **서버 파서가 먼저 거부하는 경우(앱 계층 규칙은 유지)**: 실제 서버(uvicorn 0.54 + h11 0.16)는 아래 요청을 앱에 넘기기 전에 자체 **400**으로 거부한다. 이때 응답은 앱이 만들지 않으므로 `{"error": ...}` 형식과 보안 헤더가 없을 수 있다. 본문을 읽지 않고 요청이 처리되지 않으므로 보호 목적(상한 우회·500 방지)은 지켜진다.
  - `Transfer-Encoding`이 `chunked`가 아닌 값(예: `identity`, `gzip, chunked`)이거나 헤더 이름 형식이 잘못된 경우(`Transfer-Encoding :`)
  - 숫자가 아니거나 비정상적으로 긴 `Content-Length`(예: `"9"*5000`, `"0"*5000 + 길이`)
  - 값이 서로 다른 `Content-Length` 중복(`10`, `20`)
  - 값이 같은 `Content-Length` 중복(`10`, `10`)은 h11이 하나로 합쳐 앱에 넘기므로 앱의 2번(411)에 걸리지 않고 라우터까지 간다. h11은 그 길이만큼만 읽으므로 우회가 아니다.
  - 그래서 1~3번의 411/413 규칙은 h11이 아닌 ASGI 서버를 위한 방어로 유지하고, **설계값(411/413) 자체는 단위 테스트(TestClient)로 검증한다.** 실제 서버를 쓰는 인수·E2E 테스트는 위 첫 세 가지 요청에 대해 "400 또는 설계값(411/413), 500·2xx 아님, DB 변화 없음"으로 판정하고, 같은 값 중복은 "411 또는 라우터 판정(그 길이만큼의 본문으로 처리), 500 아님"으로 판정한다. 서버 파서를 바꾸거나(httptools 등) 앱 앞단에 400 처리를 추가하지 않는다.
- 처리되지 않은 예외의 500 응답은 이 미들웨어를 거치지 않으므로 `errors.py::_handle_unexpected`가 같은 헤더를 직접 붙인다(위 errors.py 절).

POST_CONTENT_MAX_LENGTH = 5000

def validate_post(title: str, content: str) -> None:

## 통합 검증 시나리오
qa가 `make e2e`(ui·api)와 `tests/acceptance/`로 확인하고, M1 시나리오 1~10을 회귀로 다시 돌린다. 사용자 A·B는 실행마다 고유 아이디(`u` + 타임스탬프)를 쓴다. E2E DB는 한 실행 안에서 다른 테스트와 공유되므로, 개수가 정확해야 하는 검증(빈 목록, 정확히 11개)은 인수 테스트(새 DB)에서 하고 E2E는 아래처럼 상대 값으로 확인한다.

1. 빈 목록(AC-11): 인수 테스트에서 새 DB의 `GET /api/posts`가 `{"items": [], "total": 0, "page": 1, "size": 10}`. E2E에서는 `page.route`로 `GET /api/posts`(쿼리 유무 무관) 응답을 위 빈 목록 JSON으로 바꾼 뒤 `/`에 "게시글이 없습니다"가 보이고 "페이지 이동" nav가 없다.
2. 비로그인 글쓰기 차단(AC-17): 비로그인으로 `/`에 "글쓰기" 링크가 없고 "글을 쓰려면 로그인해 주세요."와 "로그인하러 가기"가 보인다. `/posts/new`로 직접 가도 폼 없이 같은 안내가 보인다. API로 `POST /api/posts`를 쿠키 없이 보내면 401 `unauthenticated`이고 `total`이 그대로다.
3. 작성(AC-18, AC-19, AC-20): A로 가입·로그인 → "글쓰기" → 제목을 비우고 저장하면 "제목을 입력해 주세요.", 101자 제목이면 "제목은 100자 이하여야 합니다."가 보이고 글이 생기지 않는다. 제목 100자·여러 줄 내용으로 저장하면 `/posts/{id}` 상세로 이동하고 작성자가 A, 줄바꿈이 유지된다.
4. 상세 표시(AC-15): 로그아웃 후 같은 상세 URL에서 제목·내용·작성자 아이디·`YYYY-MM-DD HH:mm` 형식 시각이 보이고, 그 시각은 API `created_at`(UTC)에 9시간을 더한 값이다.
5. 목록·페이지(AC-12, AC-13, AC-14): A가 API로 글을 11개 더 만든다. 비로그인으로 `/`에서 1페이지에 10개가 최신순(방금 만든 마지막 글이 맨 위)으로 보이고 "페이지 이동" nav와 "다음"이 있다. "다음"을 누르면 2페이지 항목이 보인다. `/?page=0`, `/?page=-1`, `/?page=abc`는 1페이지 내용과 "1 / N", `/?page=99999`는 마지막 페이지 "N / N"이 보인다. 인수 테스트(새 DB): 글이 정확히 10개면 `total=10`이고 `?page=2`도 1페이지로 보정된다(페이지가 하나뿐). 11개면 1페이지 10개, 2페이지 1개다. 페이지 이동 UI가 10개 이하에서 없는 것은 PostListPage 단위 테스트와 `page.route`로 `total=10` 응답을 준 E2E로 확인한다.
6. XSS(AC-25): 제목 `<script>alert(1)</script>`, 내용 `<img src=x onerror=alert(1)>`로 글을 쓴다. `page.on("dialog")`가 한 번도 불리지 않고, 상세와 목록에 입력한 글자 그대로 보인다.
7. 수정(AC-21): A가 자기 글 상세에서 "수정" → 초기값이 채워진 폼 → 제목·내용을 바꿔 저장하면 상세로 이동해 바뀐 내용이 보이고, `/` 목록에도 바뀐 제목이 보인다. 내용을 공백만으로 바꾸면 "내용을 입력해 주세요."가 보인다.
8. 권한 화면(AC-23): B로 로그인해 A의 글 상세를 열면 "수정" 링크와 "삭제" 버튼이 없다. B가 `/posts/{A글}/edit`로 직접 가면 "본인이 작성한 글만 수정할 수 있습니다."가 보이고 폼이 없다. 비로그인으로 A의 글 상세에도 두 버튼이 없다. 목록에는 A로 로그인해도 수정·삭제 버튼이 없다.
9. 권한 API(AC-24): B의 쿠키로 A의 글에 `PUT`(정상 본문)과 `DELETE`를 보내면 둘 다 403 `forbidden`이고, 이후 `GET`의 제목·내용이 그대로다. 쿠키 없이 보내면 401 `unauthenticated`. B가 빈 제목으로 `PUT`해도 422가 아니라 403이다.
10. 삭제(AC-22, AC-16): A가 자기 글 상세에서 "삭제" → 확인 창을 취소(`dialog.dismiss()`)하면 그대로 남는다. 다시 눌러 수락(`dialog.accept()`)하면 `/` 목록으로 이동하고 그 글이 목록에 없다. 같은 상세 URL로 가면 "게시글을 찾을 수 없습니다."가 보이고 `GET /api/posts/{id}`는 404 `post_not_found`다. `/posts/abc`, `/posts/0`, `/posts/99999999`도 같은 안내다.
11. 요청 보호(보안 조건): `POST /api/posts`에 65537바이트 이상 JSON 본문 → 413 `payload_too_large`. 실제 백엔드(8001)에 `Content-Length: 10`과 `Transfer-Encoding: chunked`를 함께 붙여 청크로 큰 본문(예: 2MB 가입 JSON)을 보내면 411 `length_required`이고 그 사용자는 생기지 않는다(Playwright `request`가 두 헤더를 함께 보내지 못하면 Node `net` 소켓으로 원문 HTTP를 보낸다). `Transfer-Encoding: identity`, 비정상 `Content-Length`, 값이 다른 중복 `Content-Length`는 서버 파서가 400으로 먼저 거부할 수 있으므로 "400 또는 411/413, 500·2xx 아님, DB 변화 없음"으로 판정한다(`register_body_limit_middleware` 아래 설명). 모든 API 응답에 `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy` 헤더가 있다. 백엔드(8001)의 `/docs`, `/openapi.json`은 404다. `DELETE`를 `Content-Type: text/plain`으로 보내면 415다. 교차 출처 `Origin`을 붙인 `OPTIONS /api/posts` 응답에 `Access-Control-Allow-Origin`이 없다.
12. 회귀: M1 통합 검증 시나리오 1~10(가입·로그인·새로고침 유지·로그아웃·쿠키 속성)이 모두 통과한다. `/`의 제목 "게시판"은 유지된다.
