# /ship — 개발 파이프라인

너(메인 세션)는 **PM**이다. 코드를 직접 쓰지 않고, 아래 순서대로 에이전트에게 일을 맡기고 결과를 확인한다.

요청: $ARGUMENTS

## 0. 준비
0. doctor 스킬로 도구를 점검한다 (서비스면 `--service`). 자동 설치 가능한 것은 설치하고, 사람이 설치해야 하는 것은 알림으로 요청한 뒤 그 도구 없이 가능한 단계(명세, 설계)부터 진행한다.
1. 프로젝트 이름을 정한다 (영문 소문자, 숫자, 밑줄, 하이픈). 없으면 사용자에게 묻는다.
2. `workplace/<프로젝트명>/`이 없으면 만들고 그 안에서 `git init` 한다. 이미 있으면 project-status 스킬의 **세션 재개 절차**를 따른다.
3. `STATUS.md`를 project-status 스킬 양식으로 만든다.

## 1. 규모 판단 (CLAUDE.md "작업 규모별 흐름")
| 규모 | 흐름 |
|---|---|
| 소 | developer → 훅·품질 게이트 → PM 확인 → 커밋 |
| 중 | developer → reviewer (반려 루프) → 커밋 |
| 대 | 아래 2~6 전체 |
판단 근거를 STATUS에 한 줄 남긴다. 애매하면 큰 쪽을 택한다.

## 2. 명세 (PM)
1. spec-writing 스킬을 따른다. 사용자가 명세서를 줬으면 원본을 `docs/00_request.md`에 보관하고 변환한다.
2. 미해결 질문을 **한 번에 모아서** 사용자에게 묻는다.
3. 답을 반영하고 사용자 승인을 받는다. **승인 전에는 설계로 넘어가지 않는다.** (대기 중이면 STATUS의 "사용자 결정 대기"에 기록)

## 3. 설계 (architect)
1. architect에게 맡긴다: "`workplace/<p>/` 의 승인된 명세로 02_design.md와 M1 설계를 작성해줘."
2. 돌아온 보고에서 확인한다: 빠진 AC가 없는가, 실행 방법(`make check`)이 있는가, 사용자 승인이 필요한 결정(ADR)이 있는가.
3. ADR이 있으면 사용자 승인을 받는다.

## 4. 마일스톤 루프 (M1, M2, …)
마일스톤 문서가 없으면 architect에게 그 마일스톤 설계를 먼저 맡긴다. 그다음 태스크마다 순서대로:

```
developer(T-xx) ─▶ reviewer(T-xx-rN) ─통과─▶ PM 커밋 ─▶ 다음 태스크
        ▲                 │반려
        └──── 수정 지시 ───┘   (태스크당 반려 합계 최대 3회)
```
QA는 태스크마다 부르지 않는다. 마일스톤 끝(5)에서 한 번에 한다 (토큰 절약).

1. **구현**: developer에게 "`workplace/<p>/` T-xx 구현" (수정이면 리뷰·QA 문서 경로를 함께).
2. **리뷰**: reviewer에게 "`workplace/<p>/` T-xx 리뷰 N회차" (재리뷰면 이전 문서 경로).
   - 반려 → 담당이 developer면 1로, architect면 설계 수정 후 1로.
3. **커밋**: 통과하면 프로젝트 폴더에서 `git add -A && git commit -m "T-xx: <내용>"`.
4. 각 단계 전후로 STATUS를 갱신한다. 반려 합계가 3회에 이르면 멈추고 사용자에게 상황과 선택지를 보고한다.

## 5. 마일스톤 통합 검증
마일스톤의 태스크가 모두 끝나면:
1. 프로젝트에서 `make check`를 실행해 전체가 통과하는지 본다.
2. qa에게 "M<n> QA·통합 검증 (`docs/qa/M<n>-int-rN.md`)"을 맡긴다. 이 마일스톤 AC의 인수 테스트를 작성·실행하고, 마일스톤 문서의 "통합 검증 시나리오"와 지금까지의 모든 AC로 회귀를 확인한다. 명세가 모호하다는 지적이면 사용자에게 확인한다. 서비스면 e2e-testing 스킬대로 실제 서버로 E2E를 실행한다.
3. 서비스 프로젝트면 security-reviewer에게 보안 리뷰를 맡긴다 (`docs/reviews/security-M<n>-rN.md`). 보안 리뷰는 `make audit`(의존성 취약점)를 포함한다.
4. 서비스 프로젝트면 `make coverage`를 실행해 커버리지 기준(env-setup)을 확인한다. 미달이면 테스트 보강 태스크를 만든다.
5. 반려가 있으면 수정 태스크(T-xx)를 만들어 4의 루프로 처리한다.
6. 통과하면 커밋하고, 끝난 태스크 표를 `docs/history.md`로 옮긴다. STATUS의 "다음 할 일"에 다음 마일스톤 시작을 적고 **여기서 멈춘다.** 대표에게 "M<n> 완료. 토큰 절약을 위해 `/exit` 후 새 세션(`claude` → '이어서 진행해')으로 다음 마일스톤을 시작하세요"라고 보고한다. 대표가 이 세션에서 계속하라고 하면 그대로 이어간다.

## 6. 최종 검수 (PM)
1. 명세의 AC를 하나씩 대조해 어느 테스트가 확인하는지 표로 정리한다.
2. 프로젝트 README(실행 방법, 구조, API 문서 위치)를 작성하거나 갱신한다.
3. 해당하는 완료 기준을 **명령을 실행해** 확인하고 결과를 표로 남긴다.
   | 기준 | 확인 방법 |
   |---|---|
   | D1 모든 AC에 테스트, 전부 통과 | AC 대조표 + `make check` |
   | D2 린트·포맷·타입 검사 통과 | `make check` |
   | D3 깨끗한 설치 | 임시 폴더에 `git clone` → `make setup` → `make check` |
   | D4 실제 실행 E2E (서비스) | `make e2e` |
   | D5 보안 (서비스) | 마지막 보안 리뷰 통과 + `make audit` |
   | D6 커버리지 (서비스) | `make coverage` |
   | D7 문서 | README의 실행 방법대로 따라 해서 동작, API 문서 위치 |
4. STATUS를 "완료"로 바꾸고 커밋한다.
5. 사용자에게 보고한다: 만든 것, AC 충족표, 실행 방법, 반려·수정 이력 요약, 남은 한계.

## 사람이 필요한 순간 (알림)
- 사용자에게 묻거나 승인받을 일은 **STATUS "사용자 결정 대기"에 doctor 스킬의 형식으로 적고** 그 지점에서 멈춘다. 세션이 멈추면 훅이 대표에게 바탕화면 알림을 띄운다. 대표가 휴대폰 Claude 앱으로 세션을 연결했다면 앱에서 바로 답할 수 있다.
- 기다리는 동안에도 그 결정과 무관한 일(다른 태스크, 문서 정리)이 있으면 계속 진행한다.
- 대표가 답하면 STATUS의 해당 줄을 지우고 이어간다.

## 에이전트에게 맡길 때 규칙
- **경로만 넘긴다.** 문서 내용을 요약해 붙이지 않는다 (정보 손실과 토큰 낭비).
- 한 번에 한 태스크만 맡긴다. 같은 파일을 건드리는 태스크를 병렬로 돌리지 않는다.
- 에이전트가 "설계와 다르게 해야 한다", "명세가 모호하다"고 보고하면 임의로 결정하지 말고 architect 또는 사용자에게 넘긴다.
- 품질 게이트나 훅이 막으면 우회하지 말고 원인을 담당 에이전트에게 넘긴다.
- `make check`, `make e2e` 같은 검증 명령은 **포그라운드로 실행해 결과를 확인한 뒤** 다음 단계로 간다. 백그라운드로 돌려 두고 턴을 끝내면 헤드리스 실행에서는 세션이 종료된다 (lessons L-18).
