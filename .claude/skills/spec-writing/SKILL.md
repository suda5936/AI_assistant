# 명세 작성 규칙

## 원칙
1. **검증 가능하게**: 모든 완료 기준은 테스트로 참/거짓을 판정할 수 있어야 한다. "빠르게", "편하게", "적절히" 같은 표현 대신 수치나 구체적인 결과로 쓴다.
2. **범위를 닫는다**: 하지 않을 것(제외 범위)을 반드시 적는다. AI는 시키지 않은 기능을 덧붙이는 경향이 있다.
3. **추측하지 않는다**: 요청에 없는 결정은 "미해결 질문"에 적고 사용자에게 묻는다. 질문이 남아 있으면 상태는 "초안"이다.
4. **짧게 쓴다**: 명세는 모든 에이전트가 읽는 문서다. 배경 설명보다 완료 기준에 집중한다.

## 완료 기준(AC) 작성법
- 번호: `AC-1`, `AC-2`, … (한 번 붙인 번호는 바꾸지 않는다. 삭제하면 "삭제됨"으로 표시)
- 형식: **[상황]에서 [행동]하면 [기대 결과]가 된다.**
- 정상 흐름뿐 아니라 **잘못된 입력, 빈 값, 경계값** 상황도 AC로 쓴다.

좋은 예:
- AC-1: 할 일 목록이 비어 있을 때 `list` 명령을 실행하면 "할 일이 없습니다"를 출력한다.
- AC-2: 제목 없이 `add` 명령을 실행하면 오류 메시지를 출력하고 종료 코드 1로 끝난다.

나쁜 예:
- 목록을 보기 좋게 출력한다. (판정 불가)
- 오류를 적절히 처리한다. (무엇이 적절한지 불명확)

## 템플릿

```markdown
# <프로젝트명> 요구사항 명세

- 상태: 초안 | 승인됨
- 규모: 소 | 중 | 대
- 요청 원문:
  > 사용자가 한 요청을 그대로 인용

## 목적
무엇을 왜 만드는가 (1~3문장)

## 범위
- 포함: …
- 제외: …

## 완료 기준
- AC-1: …
- AC-2: …

## 제약 조건
사용 언어, 실행 환경, 성능, 외부 라이브러리 제한 등 (없으면 "없음")

## 미해결 질문
- Q1: … (답변: 미정)
```

## 사용자가 명세서를 직접 준 경우
사용자는 워드, 노션, 메모 등 자유 형식의 명세서를 줄 수 있다. PM은 그것을 **그대로 쓰지 않고** 이 템플릿으로 변환한다.
1. 원본을 `docs/00_request.md`에 그대로 보관한다 (요약하지 않는다).
2. 원본의 요구를 하나씩 AC로 옮긴다. 원본 문장이 판정 불가능하면("빠르게", "깔끔하게") 수치나 결과로 바꾼 안을 만들어 미해결 질문으로 확인한다.
3. 원본에 없는 오류·빈 값·경계 상황을 찾아 AC 후보로 제안한다.
4. 원본에 없는데 꼭 정해야 하는 것(저장 방식, 인증 여부, 대상 사용자 등)을 미해결 질문으로 묻는다.
5. 원본의 요구 중 AC로 옮기지 않은 것이 없는지 마지막에 대조한다.

## 마일스톤으로 나누기 (AC가 10개를 넘거나 기능 묶음이 여러 개일 때)
- 사용자가 **혼자서도 쓸 수 있는 기능 묶음** 단위로 나눈다. 예: M1 회원가입·로그인, M2 게시글 CRUD, M3 댓글.
- 앞 마일스톤만 완성돼도 동작하는 순서로 배치한다 (M1 없이 M2가 성립하지 않으면 M1이 먼저).
- 명세의 "범위" 아래에 마일스톤 표를 둔다.

```markdown
## 마일스톤
| ID | 이름 | 포함 AC |
|---|---|---|
| M1 | 회원가입·로그인 | AC-1 ~ AC-6 |
| M2 | 게시글 | AC-7 ~ AC-15 |
```

## 승인 절차
1. PM이 초안을 쓰고 미해결 질문을 사용자에게 묻는다.
2. 답변을 반영하고 질문이 모두 해결되면 사용자에게 승인을 요청한다.
3. 사용자가 승인하면 상태를 "승인됨"으로 바꾼다. **승인 전에는 설계 단계로 넘어가지 않는다.**
4. 승인 후 요구사항이 바뀌면 AC를 수정하고 변경 사실을 `STATUS.md`에 기록한 뒤 다시 승인받는다.
