# 설계 문서 작성 규칙

## 원칙
1. **추측 없이 구현 가능하게**: developer가 설계만 보고 구현할 수 있어야 한다. 함수 이름, 인자, 반환값, 발생하는 예외까지 적는다. 함수 본문(구현 코드)은 쓰지 않는다.
2. **모든 AC를 연결한다**: 명세의 모든 AC가 "어디서 구현되고 어떤 테스트로 확인되는지" AC 추적표에 있어야 한다. 빠진 AC가 있으면 설계 미완성이다.
3. **가장 단순하게**: 요구를 만족하는 가장 단순한 구조를 고른다. 명세에 없는 확장성을 미리 설계하지 않는다.
4. **되돌리기 어려운 결정은 승인받는다**: 기술 스택, 외부 라이브러리 추가, 데이터 저장 방식은 PM을 거쳐 사용자 승인을 받는다.
5. **실행 방법을 반드시 적는다**: 실행 명령과 테스트 명령이 없으면 qa와 훅이 무엇을 돌릴지 알 수 없다.

## 템플릿

```markdown
# <프로젝트명> 설계

- 명세: docs/01_spec.md
- 상태: 초안 | 확정

## 개요
전체 구조를 3~5문장으로 설명

## 기술 스택
| 항목 | 선택 | 이유 |
|---|---|---|
| 언어 | Python 3.12 | … |
| 테스트 | pytest | … |

## 폴더 구조
```
src/<패키지명>/
├── main.py        # 진입점
└── …
```

## 모듈과 인터페이스
### <모듈명> (src/<패키지명>/<파일>.py)
역할: 한 줄 설명

```python
def add_task(title: str) -> Task:
    """할 일을 추가한다.
    Raises: ValueError - title이 비어 있을 때
    """
```

## 데이터 모델
주요 데이터 구조와 저장 방식 (파일, DB 등)

## 오류 처리
어떤 상황에서 어떤 예외·메시지·종료 코드를 내는지

## 실행 방법
- 설치: `…`
- 실행: `…`
- 단위 테스트: `…` (tests/unit/)
- 인수 테스트: `…` (tests/acceptance/)

## AC 추적표
| AC | 구현 위치 | 단위 테스트 |
|---|---|---|
| AC-1 | src/…/x.py::func | tests/unit/test_x.py |

## 태스크 목록
| ID | 내용 | 관련 AC | 선행 태스크 |
|---|---|---|---|
| T-01 | … | AC-1, AC-2 | - |
| T-02 | … | AC-3 | T-01 |
```

## 태스크 나누는 법
- 태스크 하나는 **리뷰 한 번에 볼 수 있는 크기**로 한다. (대략 파일 1~3개, 코드 200줄 이하)
- 순서대로 할 수 있게 선행 태스크를 적는다.
- 태스크마다 관련 AC를 적어, 어떤 태스크가 어떤 요구를 채우는지 추적한다.

## 설계를 바꿔야 할 때
- developer나 reviewer가 설계 문제를 발견하면 PM에게 보고한다.
- architect가 설계를 고치고, 바뀐 부분과 이유를 문서 맨 아래 "변경 이력"에 적는다.
