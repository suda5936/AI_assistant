# 설계 문서 작성 규칙

## 원칙
1. **추측 없이 구현 가능하게**: developer가 설계만 보고 구현할 수 있어야 한다. 함수 이름, 인자, 반환값, 발생하는 예외까지 적는다. 함수 본문(구현 코드)은 쓰지 않는다.
2. **모든 AC를 연결한다**: 명세의 모든 AC가 "어디서 구현되고 어떤 테스트로 확인되는지" AC 추적표에 있어야 한다. 빠진 AC가 있으면 설계 미완성이다.
3. **가장 단순하게**: 요구를 만족하는 가장 단순한 구조를 고른다. 명세에 없는 확장성을 미리 설계하지 않는다.
4. **되돌리기 어려운 결정은 승인받는다**: 회사 표준 스택(`docs/adr/` 참고)과 다른 기술, 외부 라이브러리 추가, 데이터 저장 방식은 `docs/adr/`에 기록하고 PM을 거쳐 사용자 승인을 받는다.
5. **실행 방법을 반드시 적는다**: env-setup 스킬의 표준 명령(`make setup`, `make check` 등)을 쓴다. 실행 명령이 없으면 qa와 훅이 무엇을 돌릴지 알 수 없다.

## 문서 구성 (두 단계)
| 문서 | 내용 | 언제 |
|---|---|---|
| `docs/02_design.md` | 전체 구조, 기술 스택, 폴더 구조, 공통 데이터 모델, (서비스) API 계약·DB 스키마, 실행 방법, **마일스톤 목록** | 프로젝트 시작 시 한 번, 이후 변경 시 갱신 |
| `docs/milestones/M<번호>.md` | 그 마일스톤의 인터페이스 상세, AC 추적표, 태스크 목록 | 마일스톤을 시작할 때마다 |

작은 프로젝트도 마일스톤은 최소 하나(`M1`)를 둔다. 문서를 나누는 이유는 에이전트가 **지금 필요한 부분만 읽게** 해서 토큰을 아끼기 위해서다.

## 02_design.md 템플릿

````markdown
# <프로젝트명> 설계

- 명세: docs/01_spec.md
- 상태: 초안 | 확정

## 개요
전체 구조를 3~5문장으로 설명 (필요하면 mermaid 다이어그램)

## 기술 스택
| 항목 | 선택 | 이유 |
|---|---|---|
| 언어 | Python 3.12 | 회사 표준 |
| 테스트 | pytest | 회사 표준 |

## 폴더 구조
```
src/<패키지명>/
├── cli.py         # 사용자 입출력 전용 (print 허용)
└── …
tests/
├── unit/          # developer
└── acceptance/    # qa
```

## 공통 데이터 모델
주요 데이터 구조, 저장 방식 (파일, DB 등)

## API 계약 / DB 스키마
(서비스 프로젝트만. api-design 스킬의 형식으로)

## 오류 처리
어떤 상황에서 어떤 예외·메시지·종료 코드(또는 HTTP 상태)를 내는지

## 실행 방법
| 명령 | 하는 일 |
|---|---|
| `make setup` | 의존성 설치 |
| `make check` | 린트 + 타입 + 단위·인수 테스트 (품질 게이트가 사용) |
| `make run` 또는 `make dev` | 실행 |

## 마일스톤
| ID | 이름 | 포함 AC | 선행 |
|---|---|---|---|
| M1 | … | AC-1 ~ AC-4 | - |

## 변경 이력
| 날짜 | 바뀐 부분 | 이유 |
````

## milestones/M<번호>.md 템플릿

````markdown
# M1: <마일스톤 이름>

- 포함 AC: AC-1, AC-2, AC-3
- 상태: 설계 | 진행 | 완료

## 모듈과 인터페이스
### <모듈명> (src/<패키지명>/<파일>.py)
역할: 한 줄 설명

```python
def add_task(title: str) -> Task:
    """할 일을 추가한다.
    Raises: ValueError - title이 비어 있을 때
    """
```

## AC 추적표
| AC | 구현 위치 | 단위 테스트 |
|---|---|---|
| AC-1 | src/…/x.py::func | tests/unit/test_x.py |

## 태스크
| ID | 내용 | 관련 AC | 선행 | 예상 파일 |
|---|---|---|---|---|
| T-01 | … | AC-1, AC-2 | - | src/…/x.py, tests/unit/test_x.py |
| T-02 | … | AC-3 | T-01 | … |

## 통합 검증 시나리오
마일스톤이 끝났을 때 qa가 확인할 사용자 흐름 (예: 추가 → 목록 → 완료 표시 → 목록)
````

## 태스크 나누는 법
- 태스크 하나는 **리뷰 한 번에 볼 수 있는 크기**로 한다 (대략 파일 1~3개, 코드 200줄 이하).
- 태스크 ID는 프로젝트 전체에서 이어서 붙인다 (M1: T-01~T-04, M2: T-05~ …).
- 첫 태스크는 보통 **환경 구성**(폴더 구조, `pyproject.toml`/`package.json`, `Makefile`, `.env.example`)이다.
- 순서대로 할 수 있게 선행 태스크를 적고, 태스크마다 관련 AC와 예상 파일을 적는다.

## 설계를 바꿔야 할 때
- developer나 reviewer가 설계 문제를 발견하면 PM에게 보고한다.
- architect가 설계를 고치고, 바뀐 부분과 이유를 "변경 이력"에 적는다.
